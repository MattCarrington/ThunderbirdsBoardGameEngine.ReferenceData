# Reference Data

## Overview

The ReferenceData subsystem provides immutable, in-memory reference data used by the Thunderbirds Board Game Engine.

Examples include:

- Disaster definitions
- Character definitions
- Location definitions
- Thunderbird definitions
- Pod vehicle definitions
- Map edge definitions

Reference data is generated by explicitly running the compiler against source spreadsheets. The generated JSON snapshot is copied into Runtime and embedded when Runtime is built. An ordinary application build does not regenerate it.

The runtime does not call a separate Catalog API for static game data.

---

## Architecture

The foundational decision is recorded in
[ADR 0000: Snapshot-based Reference Data](../docs/architecture/decisions/0000-snapshot-based-reference-data.md).
The sections below describe the current implementation.

The system consists of two main parts:

### Compiler

The ReferenceData compiler:

1. Reads source spreadsheets
2. Validates the source data
3. Builds a strongly typed snapshot
4. Serialises the snapshot to JSON

### Runtime

When the registered snapshot and catalogs are first resolved, Runtime:

1. Loads the embedded snapshot
2. Validates snapshot compatibility
3. Builds immutable in-memory catalogs
4. Exposes read-only lookup interfaces to consumers

## Runtime Catalogs

The following catalogs are publicly exposed to consumers:

- `IDisasterDefinitionCatalog`
- `ICharacterDefinitionCatalog`
- `ILocationDefinitionCatalog`
- `IDisasterBonusKeyDefinitionCatalog`
- `IThunderbirdDefinitionCatalog`
- `IMapEdgeDefinitionCatalog`
- `IFabCardDefinitionCatalog`
- `IEventCardDefinitionCatalog`

Catalogs provide:

- Read-only enumeration and lookup operations appropriate to each catalog.

All catalogs are immutable and registered as singletons.

### Consumption and construction

Applications obtain definitions through Runtime catalog interfaces and read their immutable properties. Definition construction belongs to the compiler, Runtime snapshot deserialization, and automated test tooling.

Definition constructors are internal. The compiler and shared test tooling have
explicit friend access; Core unit tests retain access to exercise validation.
Runtime hydrates Core definitions through explicitly attributed JSON
constructors. See the accepted [construction-boundary ADR](../docs/architecture/decisions/0007-reference-data-owned-construction.md)
for the mechanism and compatibility impact.

The dedicated `ThunderbirdsBoardGameEngine.ReferenceData.TestUtils` project owns consumer test support. Application tests use `ReferenceDefinitionFactory`, shared fixtures, or
`ReferenceDataSnapshotBuilder` in the test-only TestUtils assembly. Production
consumers should not reference that assembly. Typed identity constructors remain
public for catalogue lookups; the public snapshot envelope serves compilation
and serialization rather than application definition construction.

See the [compiler guide](../tools/README.md) for authoring and snapshot-update instructions, and [package releases](https://github.com/MattCarrington/ThunderbirdsBoardGameEngine/blob/99318f91dd6885e88b693a5be179b40b828133ac/docs/PackageReleases.md) for the existing publication process.

## Snapshot Metadata

Snapshot versions are independent of NuGet package versions. Package versions describe code releases; snapshot metadata describes the compiled artifact. The generator version records the compiler that produced the snapshot and does not need to match installed package versions. Current generation defaults are defined in [SnapshotVersions.cs](Core/SnapshotVersions.cs).

Snapshots contain the following metadata:

| Field | Purpose |
|---|---|
| `schemaVersion` | Defines the snapshot contract shape |
| `contentVersion` | Defines the reference data version |
| `generatedAt` | Snapshot generation timestamp |
| `generatorVersion` | Version of the compiler |

### Schema Version

The schema version changes when the snapshot structure changes.

Examples:

- Adding a new field
- Renaming a field
- Changing serialization shape

### Content Version

The content version uniquely identifies an immutable published snapshot across
all schema versions. It advances for a new publication whether or not the
schema changes. It does not determine whether Runtime can read that structure.

[ADR 0008](../docs/architecture/decisions/0008-reference-data-versioning-and-compatibility.md)
defines the prospective content increment policy: patch for presentation-only
corrections preserving identities and gameplay facts, minor for additions
preserving existing facts, and major for identity removals or changes to existing
gameplay facts and constraints. Published history is not renumbered.

For example, adding FAB 2 with speed 2, character capacity 2, and domain Earth uses the existing definition shape. It is a content change, provided consumers support additional identities and no new gameplay behaviour is required. Adding a `CargoCapacity` property changes the definition and snapshot contracts and requires coordinated code and artifact updates.

Runtime currently requires an exact schema-version match. Independent content delivery and package releases do not imply that arbitrary package and snapshot versions are compatible.

### Accepted evolution policy

ADR 0008 also records exact application-selected snapshot versions, immutable
publication, independent package releases, retained artifacts and provenance,
and future game pinning. These are accepted policies with incremental
implementation. Runtime currently loads one embedded snapshot; configurable
content selection, manifest verification, and historical game-specific
catalogues are not implemented. Existing snapshot metadata remains in place;
future CI will add a companion checksum/provenance manifest.

## Bonus Location Semantics

Disaster bonuses may optionally define a location.

If the location is omitted (`null`), the bonus applies at the disaster location itself.

This avoids duplicated source data and prevents location drift between disasters and bonuses.

The compiler validates that a bonus location is not explicitly set to the same location as the owning disaster.

## Runtime Relationship Contract

The compiler guarantees that relationships in a generated snapshot contain the
canonical, strongly typed identifiers of existing definitions. It establishes
referential integrity before writing the snapshot, including relationships from
disasters and map edges to locations and from disaster bonuses to their permitted
asset types.

The runtime therefore treats compiled relationships as trusted references. It
uses their typed identifiers for catalog lookups and does not:

- Resolve human-readable source names
- Generate relationship identifiers by normalizing or slugifying values
- Infer missing targets
- Repair ambiguous or invalid relationships

The runtime still applies the domain semantics of a valid relationship. For
example, an omitted disaster bonus location means that the bonus requires its
asset at the owning disaster's location, as described above.

See the compiler's
[Typed Reference Relationship Policy](../tools/README.md#typed-reference-relationship-policy)
for the authoritative rules governing identity creation and relationship
resolution.

## Future Evolution

The current implementation uses embedded snapshots.

The [Reference Data evolution plan](../docs/architecture/reference-data-evolution.md) describes an independent lifecycle, automated compilation and publishing, package consumption, and delivery through Azure Blob Storage. These are planned changes, not current Runtime capabilities. Snapshot archives already exist under `src/Archive`; automated publishing and cloud retrieval are not implemented.

Repository extraction and standalone CI are described in [ADR 0009](../docs/architecture/decisions/0009-independent-reference-data-repository.md). The extracted solution and test-support project are available here; authenticated publication and application package migration remain follow-up work.
